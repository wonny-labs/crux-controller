# Troubleshooting

Look a failure up by its message. Each row says where the message appears, the cause, the fix, and the page that
explains more. The set-up is in [Getting started](getting-started.md), and the commands to run are in the [Tutorial](tutorial.md)
and [Set up without the Dev Container](native-setup.md); CI stays the
reference for a pull request, and a local failure that CI does not show is a difference in your machine to look
at, not a reason to change a check.

A message of Docker, pip, git or GitHub that is quoted here comes from general knowledge, not from this
repository, and its wording can differ by version. The messages of the scripts of this repository are quoted from
the scripts, and a tooling test checks that they still say so. Two causes below were not reproduced and say so.

## How to read the CI logs

Open the pull request, choose the checks, and open the job that failed. The job name tells the kind of check, and
the step that failed names the command: the step names are the `name:` lines of the workflow files in
`.github/workflows/`. The table of workflows and jobs is in
[CONTRIBUTING.md](../CONTRIBUTING.md#build-and-test); this page does not copy it. Roughly, and only as a first
place to look:

- A change to a script, a test or a document fails `Tooling tests`; a changed or new C file also meets
  `Static analysis` and `Patch style`.
- A change to an include fails `Boundary check`.
- A change to `west.yml` meets `West pins`, and a change under `app/`, `conf`, overlays or `tests/native_sim`
  meets the build jobs of the configurations (`workload`, `net build` and so on) and `Budget`.
- A change to `.devcontainer/`, `scripts/dev-shell.sh` or `scripts/bootstrap.sh` meets the `Dev container` job.

Run the same command locally to see the same failure, from the folder that the step uses. GitHub keeps the logs
for a limited time (the default is 90 days), so a result that matters is copied into the pull request.
